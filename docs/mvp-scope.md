# MVP 范围（节点 0.1）

本文只冻结节点 0.1 的范围。不启动 0.2，不规定实现细节。

## 1. 一句话

输入为 Story Spec，输出为经人类主编批准后提交的 Canon；人类节点仅为该主编对候选变更的批准或拒绝。

## 2. 术语

- **Story Spec**：人类主编写定的故事规格，约束一部小说要写什么、不能写什么。
- **Canon**：经人类主编批准后提交的故事真相；Canon 的效力高于任何散文。
- **Scene Card**：一次场景生成的任务卡，规定该场景的生成边界。
- **Candidate Change（候选变更）**：从生成散文中抽取、不得直接写入 Canon 的待裁决变更。
- **Validate（校验）**：对照 Canon 与 Story Spec 检查候选变更是否可提交人类裁决。
- **Human Approve/Reject（人类批准/拒绝）**：人类主编对通过校验的候选变更作出批准或拒绝。

## 3. 用户角色

- 用户只有一名：创作者本人，同时担任主编。
- 运行环境：一台电脑、本地运行。
- 协作角色（本阶段不建评测 bot）：
  - lollibot：指挥官。
  - booniBot：一次只实现一个已冻结节点。
  - hettBot：只对照验收条件查缺口（经 Codex），不改产品决策、不改 Canon。

## 4. MVP 包含

只含已冻结的 v1 范围：

- 一个小说项目。
- 一名用户（创作者兼主编）。
- 一种语言：中文。
- 一个写作模型供应商。
- 生成单位为场景（不是章，不是全书）。
- 人类批准：候选变更必须经主编批准或拒绝后，才能提交 Canon。
- 核心闭环：Story Spec → Canon → Scene Card → Generate → Extract Candidate Changes → Validate → Human Approve/Reject → Commit Canon。
- Canon 高于散文：散文只可产生候选变更。
- 模型、实现 bot、验收 bot 均不得自动改 Canon。

## 5. 明确不包含 / 排除

下列项不在本 MVP 内（不得当作「稍后可能做」写进第 4 节）：

- 多项目
- 图数据库
- 自动批准
- 评测 bot
- 网页自动写小说
- 知识图谱
- 微调
- 多书批量生产

## 6. 关键使用流程

1. 主编给出 Story Spec。
2. 以已提交的 Canon 为真相约束。
3. 为主编指定的一个场景编写 Scene Card。
4. Generate：按该 Scene Card 生成该场景散文。
5. Extract Candidate Changes：从散文抽取候选变更。
6. Validate：校验候选变更。
7. Human Approve/Reject：主编批准或拒绝。
8. Commit Canon：仅把主编批准的变更提交进 Canon。

## 7. 数据不可变原则

- Canon 高于散文。
- 散文不得直接改写真相；只可产生候选变更。
- 只有人类主编批准后的提交才会改 Canon。
- 模型不得自动修改 Canon。

## 8. 人类批准边界

- 模型不得自动修改 Canon。
- 实现 bot（booniBot）不得自动修改 Canon。
- 验收 bot（hettBot）不得自动修改 Canon。
- 只有人类主编可以批准 Canon 变更。

## 9. 成功标准

每条均可按「有 / 无」判定；不以含糊的质量形容词作为唯一门槛。

| 编号 | 标准 | 有 / 无判定 |
| --- | --- | --- |
| S1 | 存在 Story Spec 作为输入 | 有可检查的 Story Spec 输入；无则失败 |
| S2 | 存在 Canon 作为已批准真相 | 有可检查的 Canon；无则失败 |
| S3 | 存在 Scene Card，且生成单位为场景 | 有场景级 Scene Card 与场景生成入口；若有章级或全书级生成入口则为「有越界」，失败 |
| S4 | 生成散文后存在候选变更抽取 | 有 Candidate Change 产物；散文结果直接写入 Canon 则为「无抽取边界」，失败 |
| S5 | 存在 Validate 步骤 | 有校验步骤且未通过者不能进入批准；无则失败 |
| S6 | 存在人类批准/拒绝步骤 | 有主编批准与拒绝两条路径；无人类裁决节点则失败 |
| S7 | 只有人类批准后的变更可提交 Canon | 有「先批准再提交」路径；存在自动写入 Canon 的路径则为「有自动批准」，失败 |
| S8 | 模型不得自动修改 Canon | 模型到 Canon 的自动写路径为「无」；若存在则为失败 |
| S9 | 实现 bot 与验收 bot 不得自动修改 Canon | 两 bot 对 Canon 的自动写路径为「无」；若存在则为失败 |
| S10 | 仅一个小说项目 | 可同时存在的项目数为 1；出现第二个项目入口或数据则为「有多项目」，失败 |
| S11 | 仅一名用户 | 可同时存在的用户数为 1；出现第二名用户则为失败 |
| S12 | 仅中文 | 产品语言配置仅为中文；出现第二语言生成/项目开关则为失败 |
| S13 | 仅一个写作模型供应商 | 供应商配置数为 1；出现第二供应商则为失败 |
| S14 | 单机本地运行 | 运行声明为单机本地；出现远程多机或网页自动写小说入口则为失败 |
| S15 | 排除项均未纳入本 MVP | 第 5 节所列排除项在本范围中均为「无」；任一被写入第 4 节或当作本节点交付则为失败 |

## 10. 风险与假设

**假设**

- 操作者始终是同一名主编，且在一台电脑上本地运行。
- 主编会对每条候选变更作出批准或拒绝，不存在自动批准。
- 写作模型只接一个供应商。
- booniBot 一次只实现一个已冻结节点；hettBot 只对照本文验收条件查缺口。
- 本阶段不建设评测 bot。

**风险**

- 若散文或模型绕过候选变更与人类批准，Canon 会被直接改写。
- 若生成单位扩到章或全书，会超出本节点冻结范围。
- 若引入多项目、图数据库、自动批准、评测 bot、网页自动写小说、知识图谱、微调或多书批量生产，即视为超出 MVP。
- 若把未冻结的「以后可能做」写进包含列表，验收将无法按有/无判定。
